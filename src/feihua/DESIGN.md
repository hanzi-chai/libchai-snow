# 冰雪飞花设计

本文面向维护本模块的 agent，区分输入方案本身的规则与本仓库优化器已经实现的功能。

方案规则依据（阅读日期：2026-11-10）：[方案介绍](https://input.tansongchen.com/snow-feihua/)、[拼写规则](https://input.tansongchen.com/snow-feihua/spelling)、[顶功编码](https://input.tansongchen.com/snow-feihua/basic)。实现说明依据本目录 Rust 源码；网页与代码的能力范围不同，不能由网页规则推定代码已实现全部功能。

## 设计目标与编码结构

飞花以声母和字根组合编码，常规单字最多四码。核心结构是「声母 + 正根 + 最多两个基本字根」，利用声、形信息离散汉字，同时使短码可以被后续输入顶出上屏。

| 集合 | 键位 | 用途 |
| --- | --- | --- |
| 大集合 `A` | `bpmfdtnlgkhjqxzcsryw`（20 键） | 声母、扩展字根 |
| 小集合 `B` | `aoeiuv;/`（8 键） | 基本字根 |
| 全集合 `U` | `A ∪ B ∪ {',', '.'}`（30 键） | 第二码可用范围 |

第一码为声母，`zh/ch/sh` 合到 `z/c/s`，零声母用 `r`。基本字根偏向简单笔形，扩展字根偏向常见偏旁。第三、四码只使用基本字根；同一字根在不同码位不换键，通过改变拆分粒度满足集合限制。这样既能让第二码容纳丰富的偏旁信息，又能保留后两码与下一字声母的集合区分。

合法常规全码统一落在 `AU`、`AUB`、`AUBB`，容量为 `20 × 30 × (1 + 8 + 8²) = 43800`。容量有限，因此字根选择、归并与重码之间的平衡是优化重点。

## 字形取码规则

先按字形分为不可再分部的部件或由多部分组成的复合体，再取形码；不能简单地把后三码理解为笔顺前三根。

- 部件字：取基本拆分的前三根；自身为字根时，第二码之后再重复一次该根。全码格式为 `AB`、`ABB` 或 `ABBB`。
- 复合体字：先确定正部及正根作为第二码，再从余部取至多两个基本字根，得到 `AUB` 或 `AUBB`。两部皆为字根时选左、上、外；仅一部为字根时选该部；皆非字根时选左、上、内为正部，向下逐层取左、上、外，直到字根或部件首根。
- 余部为部件时取基本拆分前两根；余部为复合体时，取前两部分各自逐层分部所得的部件首根。

分部优先利用自然间隙和上下、左右结构，但有字根优先、粘连、准包围等例外。兼容码还允许特定字优先取意符，或将常用字的意符视作字根；简码设置和测评采用兼容取法。具体例外及适用条件查阅[拼写规则](https://input.tansongchen.com/snow-feihua/spelling)，不要自行用字源或通用拆字算法替代。

## 顶功模式与扩展能力

这里 `_` 表示显式空格，`A/U/B` 表示所属集合。

| 模式 | 定位 | 单字格式 |
| --- | --- | --- |
| 二码顶（飞单） | 单字输入 | `A_`、`AU`、`AUB`、`AUBB` |
| 四码顶（飞码） | 主词辅单 | `A_`、`AU_`、`AUB`、`AUBB` |
| 五二顶（飞延） | 主单辅词 | 同二码顶；词语需空格确认 |

四码顶用各字构词码组合词码，并可追加形码消重。大字集另有保留常规码前缀的不限长扩展编码；未知读音时可用 `u` 替代声母。这些完整规则见[顶功编码](https://input.tansongchen.com/snow-feihua/basic)。

## 本仓库的数据流与实现边界

当前模块主要优化单字全码和字根安排，不是完整的输入法运行时。代码不直接分析汉字结构：候选拆分及条件已经由外部元素序列数据提供。维护取码规则时，应同时检查这些数据的生成方式。

1. `mod.rs` 构建上下文、棱镜、初始决策与条件决策空间，并把输入对象按频率降序排列。
2. 每个元素安排为直接键位、归并到另一元素或未选取。依赖经拓扑排序后线性化，归并读取目标元素的键位，未选取映射为 `0`。
3. 每个对象可有多个有序候选元素序列。预处理把条件分成全集合和小集合要求；`encoder.rs` 每次按当前布局选择第一个满足位图约束的候选，再将其四个元素映射为全码。
4. 编码器按全码哈希累计候选数；同码首项候选位置为 `0`，后续项标记为选重。因此输入频率与排序会影响首选项和加权指标。
5. `operators.rs` 从当前合法的单元素变更中均匀抽样，再沿依赖图传播，修正下游不合法安排；退火主循环由 `libchai` 提供。

`冰雪飞花编码信息` 虽保留 `简码` 字段，当前编码流程只生成全码，简码保持默认值。模块也没有上述词码组合、不限长扩展编码或 `u` 纯形模式的专门生成流程；不能把导出的全码表视作包含三种模式的完整输入方案。

### 编码表示的关键约束

- `编码` 固定为四个 `u8` 键，`0` 用于空码位，导出时过滤掉 `0`。短码应以尾部空码位补齐。
- 棱镜编号顺序是小集合 `1..=8`、大集合 `9..=28`、逗号和句号 `29..=30`、空格标记 `_` 为 `31`。这一顺序与 `全集合` 常量的枚举顺序不同。
- 哈希依赖第一码属于 `A`、第二码属于 `U`、第三四码属于 `B` 或为空；它不是任意四键序列的通用哈希。修改集合、编号或码长时，必须同时检查 `转换` 实现和编码空间大小。
- 候选序列列表必须非空，最后一项必须无条件，以保证布局变化后仍有回退候选；编码器找不到可用候选会直接失败。
- 归并及条件依赖必须保持可拓扑排序；变异传播超过 100 次或找不到合法安排会触发失败。

### 目标函数

当前最小化分数为：

```text
全码静态选重率 + 字根复杂度 × 0.0003
全码静态选重率 = 非首选对象数 / 对象总数
```

字根复杂度按安排计费：直接指定键位为 `5`，归并到 `韵-` 或 `形-` 元素为 `2`，归并到 `声-` 或其他字根为 `0`，未选取不计。键位保留项及名称含 `-` 的辅助元素跳过统计。对应实现位于 `objective.rs`。

频率加权选重率、指数加权选重率和选重数也会输出，但当前分数不使用两个加权率。指数权重为 `exp(-min(频率排序索引, 6000) / 2000)`。调整优化目标时应明确区分「报告的指标」与「参与退火的分数」；当前目标也不包含手指负荷或键对当量。

## 运行与维护

入口为 `../bin/feihua.rs`。`encode` 计算初始决策并向 `project-feihua/` 输出 `code.txt`、`dazhu.txt`；优化在各线程目录导出码表、配置及 `分析.md`。分析实际列出前 4000 个对象中的非首选全码项，不要依赖源码中遗留的「前 3000」注释。

所需配置与元素序列为根目录下的 `project-feihua/config.yaml`、`project-feihua/elements.yaml`，未随仓库提交。修改编码、目标函数、操作算子后，在具备真实数据时执行根目录 `make fed` 或 `make fe` 检查码表及指标；缺少数据时记录未验证的行为，不伪造输入。构建依赖、运行约定及产物管理见根目录 [AGENTS.md](../../AGENTS.md)。
